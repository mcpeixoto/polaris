# Releases

**Depends on:** issues, git integration, CI/CD, workflow automations.
**Depended on by:** status automations, changelogs, support integrations closing the loop with customers.

Available on **Business** (≤15 pipelines) and **Enterprise** (unlimited).

Solves: "Done" ≠ "delivered". Releases group issues into shipped units per product/environment so you can answer *is this in customers' hands, and what else shipped with it?*

## Release pipelines

One pipeline per product × environment combination. Configured in **Settings → Releases**.

| Field | Notes |
|---|---|
| Name | e.g. "iOS (production)", "Android Internal", "Linear App" |
| Type | **Continuous** (a release per deploy, specialised UI for constant flow) or **Scheduled** (release dates, optional **stages**, stages freezable to stop auto-adding issues) |
| Teams | Owning team(s) — doesn't restrict which issues can be added, but drives ownership and suggested releases |
| Access key | Per-pipeline secret for CI. **A personal API key cannot be used** |
| Path filters | Glob patterns (`mobile-ios/**`, `backend/api/**`) so only matching commits count — essential for monorepos |
| Release-notes template | Formatting for generated notes |
| Auto-generate notes | Toggle to generate notes each time a release hits production |

Linear's own pipelines, as a reference set: Android (production) — scheduled; Android Internal — continuous; iOS (production) — scheduled; iOS Nightly — continuous; iOS Internal — continuous; Linear App — continuous.

## Releases

A release = **name + commit SHA + set of associated issues**, inside a pipeline.

- Issues show their release in the properties sidebar; enable the Release display property to see it on lists/boards.
- Filter and group issues by **release**, **stage**, or **pipeline**.

## Status automations

Workflow automations can react to release events — most simply "move issues to a completed status when the release completes", optionally scoped to specific pipelines.

Recommended pattern that a clone should document too: let git automation move the issue to a *started* status named "Merged" on PR merge, and let the **release** automation mark it Done. That way integration automations downstream (Asks, Intercom, Zendesk reopen-the-conversation flows) fire when the change actually reaches customers, not when a PR merges.

## Release notes and changelogs

- Notes can be written manually or **generated by Linear Agent**, analysing the issues in a release (scheduled pipelines) or across a range of releases (continuous pipelines). Format comes from the pipeline's Template field.
- Every pipeline has a **Changelog** tab assembling its release notes chronologically — for internal review and sharing.

## CI integration

1. Create the pipeline in Settings → Releases.
2. Copy the pipeline **access key**.
3. Set **path filters** if needed.
4. Wire up the open-source release CLI (pre-built binaries per platform) or the sample GitHub Action from any CI system that can run a command-line tool.

### Continuous deployment example (GitHub Actions)

Store the pipeline key as repo secret `LINEAR_ACCESS_KEY`, then:

```yaml
name: Linear Release
on:
  push:
    branches: [main]
jobs:
  linear-release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # required for commit history
      - uses: linear/linear-release-action@v0
        with:
          access_key: ${{ secrets.LINEAR_ACCESS_KEY }}
```

On each push to main the action scans new commits since the last release for issue references (`ENG-123`), creates a release, attaches those issues, and marks it complete. The release name/version defaults to the commit SHA and can be overridden. Scheduled-pipeline variants exist in the same repo.

## What to build for a clone

- Pipeline CRUD + access-key issuance/rotation, path-filter matching against commit file lists.
- A small ingest API: `create release`, `attach issues (by identifier scan)`, `complete release`, `set stage`.
- Commit-message and PR-body scanning for issue identifiers (shared with the git integration's magic-word parser).
- Release → issue status automation hooks alongside the existing PR/commit automation hooks.
- LLM-generated release notes with a per-pipeline prompt/template.
- Changelog rendering.
- **[OPEN]** Whether releases are workspace-visible or team-scoped for permission purposes — the docs imply pipelines are configured workspace-wide with team ownership metadata only.
